# 证据分级与来源标注

拆解质量的上限由证据决定。所有进入报告的结论都必须能回到一条证据。

## 证据等级

| 等级 | 类型 | 典型来源 | 用法 |
|---|---|---|---|
| A | 一手 | 实机截图/录屏、游戏内文本、官方公告、版本更新说明、官方 FAQ、官方定价页 | 可直接作为事实写入 |
| B | 官方二手 | 官方访谈、制作人分享、出版社/平台官方页面、权威媒体首发报道 | 可作为事实，注明转述性质 |
| C | 第三方 | 玩家社区、评测文章、攻略站、榜单估算数据、UP 主视频 | 只能作为参考或交叉印证，写入时标注 |

等级不足的证据不要单独支撑关键结论；关键结论（付费设计、数值公式、留存节奏）尽量有 A 级或两条独立 C 级交叉。

## 编号与引用

- 全篇统一用 `E1…En`，每个编号只对应一条证据。
- 首次出现时登记到第 6 节证据表：`ID | 内容 | 来源（可点击短标签链接）| 时间 | 等级`。
- 来源列必须是可点击超链接，且用短标签（如「官网新手指引」「金铲铲官网」），不贴整条 URL——长 URL 会把表格挤成竖排字。链接失效就换成镜像页并注明。
- 正文引用写成 `〔E3〕`（中文方括号，避免与 Markdown 链接混淆），需要点明原话时用短引文，不改写原意。
- 来源必须带时间，版本相关证据同时记录版本号（如 2.3.1）。

## 时间可行性校验

采信之前先问：这条内容**当时可能存在**吗？

- 发布时间早于游戏上线日的，只能是预生成、模板套写或从别处搬运的内容，规则细节一律不采信。
- 发布时间早于所引版本的，不能用来描述当前版本。
- 标题含「上线前」「预测」「前瞻」的，即使数据看着具体，也只算 C 级以下。
- 同一作者同一站点批量产出的「玩法详解」，互相抄同一段话的，整体降级。
- 校验方式：用官方开服公告、版本更新公告的日期作为时间锚点，把可疑来源的发布时间与之对比，差值为负则剔除。

## 冲突登记

同名功能出现两套以上定义时，不要择一沉默处理：

1. 在报告「1.1 口径」写清采用哪一层口径；
2. 在「6.2 口径冲突」列出口径冲突：谁说什么、各是什么等级、为什么采信另一条；
3. 判定优先顺序：官方公告 > 官方站内页面 > 媒体深度稿（含实机截图）> 第三方攻略 > 创作者解读。
4. 最高等级证据与低等级证据冲突时，低等级那条不是「另一种说法」，而是「错误信息」，要明说。

## 推断的写法

- 格式：`〔推断〕结论 —— 依据：…`
- 只允许从已记录的事实推导，不允许“业内通常这样”式补全。
- 推断链超过两步时拆成两条，分别标注置信度（高/中/低）。
- 数值类推断必须写明反推过程（如“由 A 级证据的两次伤害值反推基础系数区间”）。

## 竞品对比的取证标准（补齐缺口）

横向对比最容易变成“凭印象填表”。硬标准：

0. **先证明对比成立，再填表**。两层检索：①同源机制（同一条功能链）→ ②同设计目的的其他解法。形似但设计目的不同的机制不得进表，只能在正文用一句“为何不纳入”交代。
1. **每行至少一条证据**。对比表每一行（一个维度或一个产品单元格）都要挂 A 或 B 级来源；挂不上的维度整行删除，或整表降级为「定性对比」并在表下注明“依据为笔者经验，未取证”。
2. **口径对齐再对比**。两个产品的同名功能先各自定义（第 1.1 步），确认是同一机制再进表；机制不同则单列「同问题的其他解法」，不进同一张矩阵。
3. **单产品至少两条证据**，其中一条必须是官方页面/公告（A 级），另一条可以是媒体实拍（B 级）。只靠一条 C 级文章的，标注“单一来源”。
4. **差异化结论要有机制证据**。写“国内版收紧了段位差限制”，必须给出国内版规则原文 + 海外版规则原文两处 link，不能只引国内版。
5. **禁止跨品类硬套**。付费结构、目标人群差异过大的产品（如买断单机 vs 免费手游）不做“行业惯例”式对比，只能做“不同解法”列举。
6. **表格自带来源列**。对比矩阵末尾加一列「证据」，每行填 `E7 / E14`；读者能一眼看出这行是否取证。

## 截图与图表取证

- 实机截图属于 A 级证据，但要记：**哪个界面、什么版本、什么时候截的**。用别人的截图则降为 B/C，且要标中转来源。
- 截图里的文字要能读出关键信息（数值、按钮、倒计时）。重要数值在正文再写一遍，不指望读者放大截图。
- 图表由数据生成时必须写明数据出处与口径（`E5`，2026-10 版本，官方未公布上限则图中标虚线/空白），推导出的区间在图注写“推导”。
- 无法取证的图不画；宁可少一张图，也不画“示意图”充当数据。

## 常见雷区

- 把攻略站的估算当官方数值。
- 用旧版本截图描述当前版本，未记录版本号。
- 拿同一品类不同付费结构的游戏硬套“行业惯例”。
- 只写“体验很好/很差”，没有可对照的机制事实。
- 抽样一两个界面就断言整体设计，缺少流程完整性验证。
