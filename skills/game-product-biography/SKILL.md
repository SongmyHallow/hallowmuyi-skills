# 游戏产品传记

把一款游戏的一生写成**有证据、有曲线、有因果**的传记，而不是一篇带情绪的评测。

**交付链路**：Markdown → 暗色 HTML（侧栏锚定目录 + 图表 + 节点卡）→ 飞书云文档入库（`04_分析` + 资料索引）。用户明确说不入库时才停在 HTML。

## 七段结构（顺序固定）

| 段 | 写什么 | 硬要求 |
|---|---|---|
| 1 现状侧写 | 今天的产品处境：官方口径（财报/公告/在线/流水）+ 社区舆论（Steam/TapTap/贴吧/NGA/小黑盒）+ 商业化状态 | 三方交叉，开头给一句「判词」；不许只引官方或只引情绪 |
| 2 生平年表 | 按阶段串起上线至今：草创 → 上线 → 爆发 → 平台扩张 → 波谷 → 转型 → 现状 | 5–8 个阶段，每阶段一句话讲清「发生了什么、数据怎么动」 |
| 3 关键节点 | 5–9 个波峰/波谷/转折，每个用节点卡：之前 → 当时 → 之后 | 波峰与波谷各至少 1 个；因果链至少 2 条证据 |
| 4 起伏曲线 | 2–4 张数据图：在线、流水/销量、口碑、热度 | 每图标口径、时间范围、出处；缺月留白不插值 |
| 5 兴衰解剖 | 驱动因子表：内容供给、商业化、竞品、平台/政策、社区关系、技术 | 每行给「作用方向 + 证据 + 置信度」，区分相关与因果 |
| 6 可迁移的教训 | 3–5 条，写给做产品的人 | 每条带适用边界，不写正确的废话 |
| 7 证据与存疑 | 证据表、口径冲突、存疑点、全部来源 | 来源列可点击；口径冲突必须显式登记 |

导语只放判词（≤3 行），不替代七段。

## 节点怎么判定

满足任意一条即可立项，全部不满足的只是「更新日志」，不进节点：

1. **数据拐点**：在线/流水/排名连续 2 个月变动 ≥30%，或创历史新高/新低。
2. **付费或平台变更**：买断转免费、订阅改内购、上主机/手游、跨端互通。
3. **内容大改**：新地图、新模式、大版本重做、核心战斗规则改写。
4. **外部冲击**：同品类竞品上线、行业政策、平台规则、硬件/流量迁移。
5. **公共事件**：大规模误封/外挂/平衡崩坏、出圈联动、赛事成绩、运营事故。

每个节点回答四问，缺一不写：

- **之前**：此前 3–6 个月的更新节奏、数据走势、竞品在做什么。
- **当时**：官方怎么定性、数据怎么反应、社区在骂什么/夸什么。
- **解释**：因果链写清「A 导致 B」，至少 2 条独立证据；只有时间相邻就标〔推断〕。
- **之后**：后续 3–6 个月可验证的变化（回流、流失、转型、口碑修复）。

## 流程

1. **立项卡**：产品全名、平台（端游/手游/主机分开算）、上线日、研发/发行、收费模式、当前运营状态（在运/停更/停运）、本次时间窗。缺关键信息问一句；能默认就默认并写假设。
2. **三源起底**（并行检索，见 `references/research-playbook.md`）：
   - 官方：官网更新日志/公告、财报与投资者材料、官方社媒、赛事页。
   - 平台数据：SteamDB/SteamCharts（Steam 在线）、小黑盒（含官服的全平台在线）、七麦/点点/Sensor Tower（手游流水与排名）、网吧热力榜。
   - 社区：Steam 评测、TapTap、NGA、贴吧、小黑盒、B 站/抖音高播放复盘、知乎。
3. **建年表**：先拉时间轴，再按「节点五信号」筛，不要把每个赛季都写成节点。写入 `timeline` 块。
4. **挖节点**：逐个节点做四问，写成 `node` 块；证据不足的降级为年表里的一行，不硬撑成节点。
5. **出曲线**：用 `chart` 块写 JSON 规格，构建时自动出图。至少一张在线/活跃图、一张商业或口碑图。口径不同不拼在同一张图。
6. **写正文**：按 `references/biography-blueprint.md` 的句式与字数控制，先结论后证据，一段不超过 4 行。
7. **自检与构建**：`python3 scripts/check_biography.py bio.md` 通过后，`python3 scripts/build_biography.py bio.md --title "《X》产品生平" --subtitle "……" --meta "PC;2021-08 至今;N 条证据"`。
8. **入库**（默认执行）：`python3 scripts/to_lark_doc.py bio.md --assets ./assets --out _feishu.md` 转飞书可读版（图表换浅色 PNG、节点/年表转原生表格与段落），再按 `references/lark-intake.md` 用 `docs +create --parent-token <04 目录>` 落盘，并在「游戏资料索引」加一行（资料类型=分析、时效状态按实情）。

## 说人话的写法

- 先给结论，再给证据：**「2023 年 7 月转免是第二次生命，Steam 峰值从 10 万级回到 26 万」**，而不是「通过对数据的分析我们可以发现……」。
- 用具体场景替代形容词：不说「体验变差」，说「2026 年 4 月小黑盒最低单日在线 3.7 万，较峰值 38.5 万跌去九成」。
- 数字必须带口径、时间和单位；只有区间就写区间，官方没公布就写「未公布」，不补一个好看的数字。
- 允许口语和短句，但不抖机灵；「凉了/暴死」只能作为引用，不能作为结论。
- 每个节点卡 ≤400 字；每张图下面一句话说清「这张图证明了什么」。

## 硬规则

- 一稿一证据表，正文用 `〔E1〕` 标注；证据分级见 `references/research-playbook.md`。
- 官方口径、平台口径、社区体感分开写；冲突进第 7 段，不悄悄择一。
- 不把「上线前前瞻」「停服后通稿」当事实；时间不可信的来源降级或剔除。
- 不画没有数据的图；不把两条曲线的不同口径叠在一张图上。
- 手游与端游分属两个产品，除非做 IP 层面叙事，否则不混写数据。

## 省 token 的做法

- 本文件是唯一常驻上下文；`references/` 只在对应步骤读，写完即用。
- 搜索先看摘要，命中再抓页；抓页用 `snippet` 定向取段，不整页复读。
- 图表、节点卡、HTML 骨架全部由脚本生成，正文里只写 JSON 规格和文字，不手写 SVG/CSS。
- 同一份证据只登记一次，正文引用编号；不要在多处重复贴链接和原文。
- 入库不重写正文：`to_lark_doc.py` 做确定性转换，模型只补标题、索引字段与一句结论。
